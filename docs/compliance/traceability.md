## Method and status rules

* Every MUST / binding statement in §1–§15, the §12 guardrails and R1–R17 is an atomic row.
* **Built**: merged code does it **and** a merged test demonstrates it. Where two modules must cooperate, both sides
  exist and agree on the contract in `packages/contracts/src/services.ts`. A Built row is a statement about the
  repository, not about a deployment: what a host must still do is in [gaps.md](gaps.md) (P-n).
* **Partial**: part of it is merged and tested, but a part is missing, untested or undermined by an open finding. The
  Notes column names the gap.
* **Missing**: no merged code does it. None today.
* **Process: open** and **Process: done**: an organisational obligation (CEO, compliance lead, ops); software can at
  most support it. Done means it has been carried out (the date is in Notes).
* Paths are repo-relative; `file:line` points at the decisive code. Tests are `file › "test name"` (the title as
  written in the test file; `…` marks a shortened title).
* Gap ids G-n (software) and P-n (process) refer to [gaps.md](gaps.md); O-n to the
  [threat model](../security/threat-model.md#6-requested-changes-and-open-decisions) §6.
